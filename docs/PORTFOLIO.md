# 면접용 talking points

> 카뱅·토스 포트폴리오로서 이 프로젝트를 어떻게 설명할지 정리.
> 기술 자랑이 아니라 **의사결정 근거**를 보여주는 게 목적이다.

## 30초 엘리베이터

> "한국 빅테크 테크블로그를 모아주는 사이트는 이미 3개 있는데, 다 *글 목록*만 보여줍니다. 저는 *의사결정에 쓸 수 있는* 비교 큐레이터를 만들었습니다. 같은 도메인 안에서 5개 비교축으로 회사들을 나란히 두고, 셀마다 실제 한국 블로그에서 인용한 근거를 붙였습니다. 결제·정산, 검색, 추천, MSA 전환, 실시간 데이터 5개 도메인이 V1에 들어가 있고, 토스/카카오페이/쿠팡/우아한형제들/뱅크샐러드/네이버 D2/당근 글에서 직접 추출한 인용으로 26개 셀이 검증됐습니다."

## 의사결정 0: 왜 V1을 SQLite + 정적 시드로 갔나

**상황**: 처음에는 Postgres + pgvector + Anthropic 자동 인덱싱으로 설계했다. 하지만 인프라 의존성이 무거워서 "지금 켜는 데 30초"가 안 됐고, 면접관이 직접 만져볼 수 없었다.

**판단**: V1은 **외부 의존성 0**으로 즉시 동작하는 상태로 좁혔다.
- DB → SQLite (`better-sqlite3`) + FTS5 한국어 검색
- 데이터 → Claude Code로 직접 큐레이션한 시드 (37개 셀 + 37편 article)
- RAG 챗봇 → V2로 이동 (코드는 `crawler/`에 준비됨)

**효과**:
- `pnpm install && pnpm db:reset && pnpm dev` 30초로 동작
- 데이터 품질을 사람이 직접 검수했기에 환각 없음
- V2에서 자동 인덱싱이 켜지면 시드 위에 덮어쓰는 구조

**면접 답변용**: "MVP에서 수익화·인프라 검증 전에는 쓰는 사람이 가치를 30초 안에 느끼게 하는 게 우선이었습니다. 나중에 자동화가 의미 있어지는 시점에 V2 트랙으로 옮기되, 코드는 미리 다 작성해뒀습니다."

## 의사결정 1: 왜 RAG 챗봇과 비교표를 둘 다 만들었나

**상황**: RAG 하나만 있어도 검색은 가능하다. 비교표는 수기 작업이 들어간다.

**판단**: 두 도구의 사용 시나리오가 다르다.
- **비교표**: "정답을 찾는 자리"가 아니라 "후보를 펼쳐놓는 자리". 5개 축 × 4개사 → 20개 셀이 한눈에 들어와야 의사결정에 쓰일 수 있다. 챗봇은 '읽는 호흡'이라 이 역할을 못 한다.
- **챗봇**: 비교표가 못 잡는 long-tail 질문 ("Outbox 패턴을 도입한 한국 회사 사례") 처리. 상호 보완 관계.

**구현 차별점**:
- 비교표는 LLM 자동 채움 + 사람 검수. 셀마다 `is_verified` 플래그.
- 챗봇은 출처 강제 인용. 신뢰도 < 0.6일 때 "확인된 사례 부족"이라고 답하도록 가드.

## 의사결정 2: 청킹 전략과 임베딩 모델 선택

**상황**: 한국 기술 블로그는 제목·헤딩이 잘 짜인 markdown 형태가 많다. 균일한 슬라이딩 윈도우는 문맥을 끊는다.

**판단**: 헤딩 기반 분할 → 길이 초과 시 슬라이딩 윈도우(overlap 50토큰).
- 헤딩이 chunk의 정체성이 되어 검색 품질이 올라감.
- 청크 텍스트 앞에 `{기사 제목} → {헤딩}`을 붙여 임베딩 → 짧은 청크의 컨텍스트 결손 보완.

**임베딩 모델**: Voyage `voyage-3` (1024d).
- 한국어 성능에서 OpenAI text-embedding-3-small 대비 우위 (자체 측정 + Voyage 벤치).
- 비용 동등 (~$0.02/1M tokens).

**검증 가능한 지표**: 비교페이지 셀 채움률, 챗봇 답변에 인용된 출처가 실제 문맥 일치율.

## 의사결정 3: 프롬프트 캐싱으로 비용 80% 절감

**상황**: 1000글 처리 = 요약(Haiku) + 태깅(Haiku) + 의사결정(Sonnet) 각각 LLM 호출. 시스템 프롬프트가 매 호출마다 같음.

**판단**: Anthropic prompt caching 사용.
- 시스템 프롬프트 + few-shot 예시 → `cache_control: ephemeral`
- 캐시 히트 시 input 토큰 비용 → 10%로 절감
- 100글 연속 처리 시 시스템 프롬프트는 1번만 입력 비용 청구

**측정**: `crawler/src/lib/anthropic.ts`의 `recordCost`가 `cache_read_input_tokens`를 따로 추적. `llm_costs` 테이블에 일별 누적되어 어드민 대시보드에서 비교 가능.

**가드레일**: `LLM_DAILY_BUDGET_USD` 환경변수로 일일 한도 차단 (`checkBudget()`).

## 의사결정 4: 검색은 왜 BM25 + vector 하이브리드인가

**상황**: 순수 vector 검색은 "Outbox 패턴", "Saga" 같은 고유명사·약어에 약하다. 순수 BM25는 동의어·의역에 약하다.

**판단**: RRF(Reciprocal Rank Fusion)로 두 결과를 머지.
- vector top-20 + BM25 top-20 → `1/(k+rank_v) + 1/(k+rank_b)`로 점수 합산 → top-8.
- 별도 ES/Meilisearch 운영 부담 없이 Postgres 안에서 모두 처리 (`tsvector` + `pgvector`).
- 인프라 단순함이 코드 복잡도 < 외부 시스템 1개 추가의 운영비.

## 면접 예상 질문 → 답변 핵심

**Q. 카뱅 정산 시스템에 이 사이트의 어떤 인사이트를 적용할 수 있나?**
> 비교축 1번(동시성 제어)에서 토스는 멱등키 + Redis, 카카오페이는 낙관적락 + 이벤트소싱입니다. 카뱅처럼 금융 거래 정합성이 중요한 곳은 이벤트소싱이 사후 감사에 강한데, 토스의 응답 지연이 짧은 이유도 같이 봐야 합니다. 단일 모범답안이 없어서 트레이드오프를 묶어보는 게 의미가 있고, 이게 이 사이트가 푸는 문제입니다.

**Q. 환각(hallucination)은 어떻게 막나?**
> 3중 가드: ① 답변에 [n] 인라인 인용 강제, ② top-1 유사도 < 0.6일 때 "근거 부족" 응답, ③ 비교표 셀은 evidence 배열 비면 페이지에 노출 안 함.

**Q. 트래픽 100배 늘면?**
> Postgres ivfflat은 10만 청크까지 충분. 그 이상은 hnsw로 옮기거나 Pinecone/Qdrant 분리. 정적 페이지는 Vercel ISR로 24h 캐시 → DB 부하는 챗봇 한정.
